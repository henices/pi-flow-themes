# pi-flow-themes — 25 pi themes from official color schemes

25 well-known color schemes ported for the [pi coding agent](https://github.com/earendil-works/pi).
All color values come from each theme's official palette (sources and pinned upstream commits are
locked in `sources/theme-sources.json`); every token's role was mapped by hand, one by one, following
the original authors' highlight specs. The theme JSON is generated by `build_themes.py` from that
mapping table, and all 25 were validated with the schema validator bundled in pi 0.85.1
(`@earendil-works/pi-coding-agent`) and actually loaded through its loader.

## Install

```bash
mkdir -p ~/.pi/agent/themes && cp themes/flow-*.json ~/.pi/agent/themes/
pi --use-theme flow-dracula      # for this run; pick and persist via /settings inside the session
pi --use-theme light/flow-nord   # follow the terminal's light/dark: built-in light on light terminals, flow-nord on dark
```

pi hot-reloads theme JSON when you edit it.

The UI panels (tool status boxes etc.) are dark, low-saturation truecolor values and need 24-bit
color end to end across the chain (pi → tmux → terminal): if the status boxes turn teal / gray,
follow [docs/truecolor.en.md](docs/truecolor.en.md)
(中文：[truecolor.md](docs/truecolor.md)).

## Design principle: the background carries state, the foreground carries identity

pi has no global background token: the canvas is the terminal's own background color, and a theme
only controls what is drawn on top of it. The 56 tokens therefore split into two layers:

- **UI layer (19 tokens, one set of constants shared by all 25 themes)** — the user message box, the
  three tool status boxes, selection, search, dividers, scrollbar, and the seven thinking-level
  borders use a single set of dark, low-saturation colors: backgrounds express state, not theme
  identity. Panels are pinned at L\\* 27.5 and stay distinguishable on mainstream terminal
  backgrounds up to L\\* 22.
- **Foreground layer (37 tokens)** — body / secondary / status line, syntax, markdown, status
  colors, accent, borders use in principle only hex values from the official palettes, with roles
  mapped per the original authors' highlight specs; body text passes 4.5:1 on every theme's own
  canvas.

The full rationale — definitions of the three metrics (contrast ratio / CIE L\\* / ΔE), the UI-layer
constant tables and measured terminal backgrounds, the brightest background each theme supports, the
known costs of sticking to official colors (`--check` lists them; left unfixed on purpose), and the
catalogue of intentional role deviations — is in
**[docs/design.en.md](docs/design.en.md)** (中文：[design.md](docs/design.md));
every number can be recomputed with `python3 build_themes.py --measure`.

## Building

`themes/` already contains the finished output. To change colors or add a theme you only ever touch
one file:

```bash
python3 build_themes.py            # regenerate themes/ from the THEMES table
python3 build_themes.py --check    # enforce contrast via FLOOR (non-allowlisted low-contrast items fail)
                                   # + per-theme canvas support ceiling + sources/theme-sources.json completeness
                                   # + near-duplicate theme report; any failure exits 1
python3 build_themes.py --preview  # also render the two preview images (needs the playwright CLI + chromium)
python3 build_themes.py --measure  # print every metric cited in the README: UI-layer L*, pairwise ΔE of the status
                                   # boxes, panel ΔL* against each terminal background, per-theme contrast tables
python3 build_themes.py --measure '#2E4931' '#414141'   # any hex values: L*a*b* for each, pairwise contrast / ΔE / ΔL*
```

Adding a theme means adding one entry to `THEMES`: hex values from the official palette plus a role
table. Body / secondary / status line, accent, borders, the three status colors, title / code /
tags, and the nine syntax roles must be spelled out; the remaining tokens fall through `DEFAULTS` to
text / muted / dim / accent and so on. Then add a source record to `sources/theme-sources.json`
(upstream repo, exact commit, files, license) or `--check` fails.

Everything — two builds byte-identical, `themes/` in sync with `THEMES`, the full `--check` gate,
and all 25 themes loaded through pi's own validator + loader — collapses into one self-contained
script, `ci/check.sh` (~8 s). How to wire it to git hooks / cron / a self-hosted forge, plus the
manual cross-check through pi's own loader, is in **[docs/ci.en.md](docs/ci.en.md)**
(中文：[ci.md](docs/ci.md)).

## Sources and licenses

All color schemes belong to their original authors (Nord, Dracula, Catppuccin, Gruvbox, Tokyo Night,
Solarized, Monokai, Kanagawa, Rosé Pine, One Dark Pro, ayu, Everforest, GitHub, Melange, Miramare,

`sources/theme-sources.json` (verified 2026-09-19). The theme JSON and the build script ship with
this repository under the MIT license (see `LICENSE`; they contain color values and role mappings
only, no upstream code), for use with the pi coding agent.

A few schemes need license notes:

- **Gruvbox**: the `morhetz/gruvbox` repository has no LICENSE file and GitHub detects no license.
  This repo only reuses its color values (a dozen-odd hex codes, no upstream code) and keeps them at
  the user's discretion; if upstream later adds a license or raises an objection, we will adjust.
- **Oceanic Next**: no LICENSE file in the repository; the README merely states "MIT Licensed".
- **Solarized**: the MIT text sits in the header of `colors/solarized.vim`; there is no standalone
  LICENSE file.
- **Tokyo Night**: Apache-2.0 (all the others are MIT).

The candidate pool also included Bearded Theme (GPL-3.0, incompatible with the MIT set) and Panda
(no license attached to the repository); neither is included for now.
